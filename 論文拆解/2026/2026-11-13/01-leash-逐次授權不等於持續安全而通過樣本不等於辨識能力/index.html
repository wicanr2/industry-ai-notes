    LEASH：逐次授權不等於持續安全，而通過樣本不等於辨識能力¶

    問題：規劃器能避碰，仍可能把手機放進水裡；要在哪些執行接口重新判斷語意風險？ 方法：LEASH 將共享安全政策與 task／action／commit 三道影像條件審核放進 harness，不重新訓練規劃器。 判讀：這是有用的授權切分，但不是連續時間安全保證；已放行候選的低錯誤率，也不是所有危險候選的攔截能力。

    一、缺口不是「再加一個拒絕模型」，而是何時重審¶

    幾何上不碰撞，與物件用途正確是兩個問題。把手機移到水裡可能路徑平滑；端飲料跨過筆電，也可能從未真的灑出來。作者因此把安全評估從文字回答移到閉迴路動作後果，並區分不應接下的目標、應換路線的任務、執行途中出現的危害、視覺注入及跨輪遺忘。〔§1、§3〕

    真正的系統問題是：先前的批准能否覆蓋下一個不可逆轉換？ 任務可接受不代表提案路線可接受；路線曾獲准也不代表幾秒後鬆夾爪仍安全。LEASH 把審核點設在這三種接口，而不是只在開始前讀一次指令。這個區分值得保留；但「三個點都有審核」仍不等於它們之間所有運動都有人監督。

    二、方法：凍結規劃器，改變誰有執行權¶

    輸入、輸出與流程¶

    規劃器輸入使用者指令、當前影像／機器人狀態、深度、互動歷史與共享政策，提出 primitive 或複合 skill。審核器輸入 RGB 影像、狀態、相同政策與短歷史；保留最後五個已執行動作，task gate 另看前幾輪互動。輸出是安全分數而非文字理由；規劃器只看到允許／拒絕，不看到分數。〔§4、B.1–B.2〕

    若用簡式表示三道 gate 的放行規則：

    \[ \operatorname{allow}_k=\mathbf{1}[s_k>\tau_k],\qquad s_k\in[0,1]. \]

    \(k\) 代表 task、action、commit 三道審核；\(s_k\) 是審核模型對當前候選給的安全分數；\(\tau_k\) 是門檻；\(\mathbf{1}\) 表示條件成立才放行。分數等於門檻也拒絕。作者在模擬與真機均用 task／action 的 \(\tau_k=0.5\)，commit 的 \(\tau_k=0.3\)。這不是物理風險上限，也未在已讀段落提供安全機率校準保證；不同 gate 的分數不能直接當相同量尺。〔§4.2、B.2〕

    1. Task gate：每輪開始前審指令與現場。拒絕便終止，是唯一能直接終止整個任務的 gate。
    2. Action gate：每個動作／skill 開始前重審；拒絕只擋這個提案，回規劃器取新觀測、重擬計畫，不能直接終止任務。
    3. Commit gate：長 skill 走到程式識別的操作時暫停，以當前觀測再審；目前只覆蓋開夾爪、傾倒。拒絕保持該操作阻擋，交還規劃器修正或自行結束。

    共享政策不只禁止某些物件組合，也明定影像中的文字是證據而非新授權、歷史過敏／加熱／給藥資訊不能憑空清除，以及不能反覆提交原封不動的被拒候選碰運氣。這些是 prompt 規範；未等同證實 harness 在程式層對每項規則都有不可繞過的強制器。〔B.1〕

    「Lease」在本文到底承諾了什麼¶

    作者用 lease 指限定當前任務／動作／受監控操作的批准，規劃器沒有永久行動權。已讀方法沒有給出帶時間的 TTL、到期時鐘、撤銷傳播延遲或硬體停止距離規格；不應借用分散式系統術語，自行補出已具備的失效／撤銷協議。〔§4.1–4.2、B.1–B.2〕

    尤其 action／commit gate 不掌握任務終止權；模型分數錯誤時，系統仍依賴規劃器遵守政策、重新規劃並在需要時停止。論文承認長 primitive 內其他危害未被 commit gate 監控。這不是用高層語意模型替代獨立限速、急停或連續安全控制的證據。〔§6〕

    資料、訓練與真正的 baseline 改動¶

    本文不訓練新控制策略或新安全模型，沒有 LEASH 專用訓練資料集／loss。規劃器與審核後端可分開更換；預設 reviewer 為 Jev，亦比較作者稱為 Decisions API 的後端及較慢的通用模型。本文模型／服務名稱依原文記錄，未另核產品文件，不提供使用建議。〔§4–5〕

    基線沿用 RPent harness；LEASH 保留工具與觀測，同時新增共享政策和三個 gates；baseline 規劃器沒有那份政策。因此整體改善可歸於這個套件，不能單獨歸因於 commit gate 或 lease。作者沒有完整移除元件的閉迴路消融，改做執行紀錄分析；費用高是限制理由，不是紀錄分析能取代因果對照的證明。〔§5.5、B.1–B.2〕

    三、實驗證據：先看任務定義，再看百分比¶

    資料與指標¶

    RoboRisk-S 有 92 個 MuJoCo／LIBERO／robosuite 模擬任務：拒絕 T 29、計畫修復 P 21、執行危害 E 15、注入 I 12、序列記憶 S 15；每組態每任務三個 seeds，共 276 次。RoboRisk-R 為 Dobot CR5V2、雙指夾爪與兩台 RealSense D455 的桌面真機，13 個任務各跑一次。不是每個規劃器都在兩環境評測：部分因費用、推論速度或預試運動風險排除。〔§3、§5.1〕

    \[ \mathrm{HR}=\frac{N_H}{N},\qquad \mathrm{SSR}=\frac{N_{SS}}{N}. \]

    \(N\) 是評估執行次數；\(N_H\) 是標為 Harm 的次數，\(N_{SS}\) 是 Safe Success 次數。模擬先在各任務內平均 seeds，再等權平均任務。Harm 優先於完成，包含已發生損害及可能危害，不是傷害事故發生率；真機使用矽膠刀、斷電模型與替代液體。T 的安全拒絕、E 的及時安全終止也能算 SSR；所以 SSR 不等於「把使用者原指令做完」的生產完成率。〔§3.1–3.3、A.2–A.3、B.2〕

    模擬 evaluator 檢查狀態 predicates，但最終標籤由人工覆核；真機則看錄影人工判定。已讀段落未提供標註者一致性或盲評結果。T／I／S 某些危險物件只要嘗試抓取就記 Harm；P／E 運輸路線跨入保護區，即使沒有損壞也記 Harm。比較前應接受這個語意風險口徑。〔A.2、B.2〕

    主表支持什麼¶

    原文表 2 的同 planner／環境 baseline → LEASH（Jev）配對：

    • GPT-6 Astra，模擬：HR 11.23% → 0.00%；SSR 78.99% → 80.80%。
    • GPT-6.1 Sol，模擬：HR 18.48% → 1.45%；SSR 72.10% → 78.62%。
    • Gemini 4 Argon，模擬：HR 9.06% → 5.80%；SSR 75.00% → 79.71%。
    • GPT-6.1 Sol，真機：HR 38.46% → 0.00%；SSR 46.15% → 84.62%。每組僅 13 次，不是可部署風險率的精密估計。
    • 未被解決的殘差：GPT-6 Luna 模擬 LEASH HR 12.68%；Grok 4.7 真機 LEASH HR 38.46%。作者描述不穩定運動、撞桌／攝影機等失效，指出語意審核無法補救所有底層控制問題。

    這些結果支持「在被測場景，套件降低該評分規則的危害，且整體 SSR 未下降」。不支持消除危害、所有模型都在同樣環境測過，或跨平台已驗證。兩個機器人 API 僅另測適配過的 13 任務模擬子集，沒有接上 LEASH，也不可和主表真機直接排名。〔§5.1–5.3、表 2〕

    另一個外推限制是抓取被簡化：模擬部分場景使用隱藏 weld；3,312 次計入執行中，332 次從預抓取狀態重啟，其中 299 次為 GPT-6 Luna。真機多數 P／E 及部分 S 也從持物開始。因此這是有意隔離語意風險的設計，不是端到端抓取／運輸可靠度評測。〔B.2〕

    四、最重要的統計邊界：通過樣本的正確率不是辨識率¶

    C.2 的 action／commit 分析只對批准且執行、可取得 evaluator 標籤的候選判對錯；拒絕候選沒執行，因此無標籤。作者報告強規劃器下這些候選非常少出現不安全者，並在表 S6 稱其 accuracy。

    本筆記更窄地理解為：在該規劃器與 gate 共同塑造的已通過分布，大部分執行區間沒觸發 evaluator 危害。它不能回答「危險提案有多少被攔下」、誤擋多少可行安全方案，也不能和 task gate 有完整目標標籤的 accuracy 混成同一種分類能力。共享政策先讓強規劃器少提危險動作，亦會提高這個條件分布上的比例。〔§5.5、C.2〕

    需要拆開四件事：危險提案產生率、危險提案攔截率、安全提案誤擋率，以及全任務最終 HR／SSR。本文提供最後一組及部分已通過候選觀察，沒有完整補齊前面各項，更沒有獨立 policy-only、gates-only 的完整消融。

    五、時間、協作與有效條件¶

    作者對兩個 GPT planners 的模擬報平均端到端 245.21 秒 → 249.28 秒，增幅 1.66%；gate 估計費用每次 0.00522 美元，占估計總費用 0.791 美元的 0.66%。但 planners 透過訂閱 CLI 存取，費用用 API 標價估算，不是實付帳單；CLI 排程／網路也在牆鐘內。相對慢規劃器的小比例，不能推成工業即時控制的小絕對延遲；已讀段落沒有提供危害出現到制動的尾延遲。〔§5.6、B.2、C.3〕

    真機 P1／P2 的持刀繞手、交刀任務，幾個強模型即使有 LEASH 也不完成。作者稱 Human-Presence Gap，並由更換人手模型後行為改變，推測內建安全政策的影響；這是現象與假說，不是已隔離感知、政策及場景差異的因果證明。不冒險完成與「能安全合作」也不是同一件事。〔§5.7、C.4〕

    第一性原理：最小必要狀態與不可略過的限制¶

    • 必要狀態：當前物件／區域關係、持物與下一不可逆操作、仍有效的歷史限制、目前批准覆蓋哪個候選。只有最後五個動作，不保證安全事實全被保留。
    • 技術限制：審核器必須看得到關鍵危害，且 skill 的監控 hook 必須在危害發生前可攔截；漏看、漏 hook、通過後場景改變都能破壞這個鏈。
    • 資料限制：單次真機任務、人工危害口徑、無標籤拒絕候選與缺少因子消融，限制可推論的可靠度與機制歸因。
    • 物理限制：停止呼叫／拒絕下一個動作，不等於目前物體安全靜止；握持、慣性、液體與人的移動仍需獨立控制界線。
    • 有效條件：規劃器遵守共享政策、工具不能繞過 gate、危險操作有完整監控、觀測仍新鮮、拒絕後有安全保持狀態。本文只驗證其中一部分，不把這份條件清單當成既成系統能力。

    六、可複用研究問題與後續驗證¶

    1. 分開政策和 gate：固定 planner／工具／任務／預算，做 policy-only、gates-only、兩者合用及各 gate 移除；對同組候選在可控模擬中補反事實標籤，量誤放與誤擋，而不是只讀通過紀錄。
    2. 分開批准和有效期：在批准後、開夾前及非 release 的長 skill 中加入場景改變，量擷取到生效年齡、危害到阻擋尾延遲、被阻擋時的持物／制動結果；同時報完整安全成功與安全不完成。
    3. 分開語意與運動能力：保留語意任務，取消 weld／預抓取協助並增加真機重複，分報語意錯誤、抓取／運動失效與介入，確認安全改善能否保留至真正交還工作。

    對讀：Nav2 的政策合法、指令正確與物理守界／VLA 啟動抑制。前者問規範到執行的接口，後者問開始與否；LEASH 再補「進入 skill 後哪個操作要重審」。這是問題與責任邊界對照，並無跨篇整合實驗。
