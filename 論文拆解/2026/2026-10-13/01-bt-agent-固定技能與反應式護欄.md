# BT-Agent：讓慢速模型選技能，讓本地護欄決定能否繼續

> 研究問題：機器人把語言模型搬到機上後，如何避免把停止動作也交給秒級推論？
> 方法核心：Actor 選擇固定技能；監督行為樹派送；技能內的本地檢查每次 tick 重驗執行條件。
> 本筆記判讀：較強證據支持結構化介面與診斷回饋；不應把共同技能層上的成功率差異解讀成行為樹本身的因果優勢。

## 1. 缺口不是只會不會規劃，而是誰能中斷

既有 LLM 機器人代理多關注下一步技能選擇或程式合成。機上部署增加另一個問題：感知、推論、控制共享資源，模型做決策時，機器人可能已經在移動。只在技能開始前驗證參數，不代表導航途中定位失效時仍能停下。

BT-Agent 不讓模型生成或修改執行中的行為樹。它讓任務層保持彈性，將可審閱、可測試的固定執行邏輯放在技能層。這與「讓 LLM 寫整棵樹」是不同介面，也不是新端到端 VLA 訓練法。

## 2. 任務、輸入輸出與兩個時鐘

### 任務定義與狀態

輸入是自然語言任務、歷史摘要、先前技能結果與具型別的物件儲存內容。Actor 接收文字和結構化資料；影像由感知技能處理，不直接等同 Actor 的觀察格式。輸出是技能名稱與參數，或完成宣告。監督樹一次執行一項技能，返回狀態和結果，再呼叫 Actor；完成宣告轉成 terminal submission，評分仍由目標規則決定。

巡檢技能包括 `query`、`surround_survey`、`navigate`、`capture`、`press`、`push`、`report`、`submit`。例如拍眼鏡，需要查場景記憶、到觀察點、確認當前可見物體，再取得新照片；舊地圖影像本身不算完成。

### 推論／控制迴圈

1. Actor 根據指令、歷史及已儲存結果選技能與參數。
2. 框架檢查參數、物件參照和必要先前觀察；未符合條件的實體技能拒絕啟動。
3. 技能內的 reactive sequence 每個 tick 檢查取消、逾時與技能專屬 guard。
4. guard 失敗則中斷分支並要求控制器停止，無須再做模型推論。
5. 失敗 leaf／guard 提供可用的診斷；Actor 可改參數、重試、換動作，或報告限制。實體動作被擋時，查詢等情境技能仍可用。

**資料與訓練目標**：本文使用既有模型，primary／transfer 比較中權重不變；161 項任務用於 prompt、harness 開發及評估，並不是新政策的訓練資料。本文沒有提出新的學習損失函數。文字環境可供未來 RL，是展望，不能寫成已完成訓練。

### 相對 baseline 真正改了什麼

主比較為 Act、ReAct、適配的 CaP-X 與 BT-Agent；同一 backend 共用指令、技能和執行檢查。不同之處是提示、動作介面、歷史處理與編排方式。CaP-X 生成／修正 Python 程式，BT-Agent 一步一步選技能。因此主成功率比較**沒有單獨移除 BT guards**，不能用來量測「有／沒有護欄」的效果。

## 3. 實驗：先拆編排能力，再看物理落差

### 場景、預算與指標

- 161 個文字任務：50 個 primary（39 Habitat 衍生、11 Isaac 衍生），另有一間 HSSD 住宅的 111 個 transfer 任務。Transfer 為 37 個家族各三種措辭，不是 111 個彼此完全獨立的場景。
- 主文字比較：Qwen3.5 NVFP4 的 4B、9B、27B、122B-A10B，各任務三個配對 seeds；B300 上 vLLM、greedy decoding。允許參考操作數三倍及 1,800 秒。
- Act／ReAct／BT-Agent 每次動作選擇上限 1,024 output tokens；CaP-X 每次程式 20,480；BT-Agent 的歷史摘要另設 512。這是不同介面的預算，不能視為相同 token 成本。
- 指標為 task-weighted success rate（按任務加權的成功率），以及 episode output tokens 的 median（中位數）／P99（第 99 百分位，觀察昂貴尾端而非最壞值）；包含失敗與 context exhaustion，未取得的 retry usage 不計。

### 作者結果與較可信的消融

表 V 中，4B BT-Agent 的 SR161 為 51.6%，ReAct 為 41.4%；9B 為 54.7% 對 49.7%。正文概括提升 10.1 與 5.0 個百分點，表格採四捨五入數值，本筆記不另重建未捨入結果。27B 的兩者 nominal SR 同為 62.9%，ReAct 的 median／P99 輸出較低：較大模型不一定需要同樣厚的 harness。

**匹配消融用另一組 fresh control**，不是拿主表當控制：9B control SR161 為 58.0%，換文字動作介面為 44.3%，把診斷簡化成技能名與 status 為 52.6%。去除 capture 專屬提示影響小。這較直接支持「結構化呼叫、資訊充足的失敗回饋」改善任務編排。

文字故障注入包括 stale／missing pose、導航未移動或到錯 viewpoint、路線阻塞、互動未完成和感知缺證。有些回報 success 卻沒有完成效果，測試代理是否只相信 status。BT-Agent 在各模型大小的故障條件中有最高觀察成功率，但仍是此技能與故障集合內的結果。

### 文字成功不是物理成功

39 個 Habitat primary 任務、四種方法、9B、三 seeds 的配對比較，共享任務和場景先驗，但各自依實際回饋決策。**只有 57.3% 的文字成功也在 Habitat 成功**；Isaac 衍生與 transfer suite 只在文字中做定量評估。39 個 task means 的 Spearman 相關為 0.61，是描述性關聯，不是部署可靠性證明。

作者以 16 個任務、八 workers 量測文字 950 episodes/hour、Habitat 87.3，報告 10.9 倍吞吐，**排除 timeout attempts**，不是實機速度提高 10.9 倍。

### 真機與失效案例

Spot 加 Jetson Thor 執行 9B Actor 與視覺技能；使用預先建好的 FARM 場景圖、waypoint graph，以及經人工校正的重大標記錯誤。推論、檢索、BT、規劃與控制在機上，**運動仍需要 operator approval**。五項任務各三次，成功 11/15；時計回報因小鐘面誤讀而出錯。

九次運動中介入，命令速度於本地接受介入後 median 19 ms 歸零，下一個模型選擇需 3.2–3.9 秒。**命令歸零不是實體速度歸零**，也不是端到端停止延遲、最壞延遲或功能安全認證。

Robosuite 的 14 項任務測技能編排，但技能是 blocking API 而非 BT。27B shared-skill CaP-X 在規則的擦拭路徑成功 14/20，BT-Agent 在其時間預算內為 0；觀察決定後續動作的三方塊重疊則為 15/20 對 4/20。程式迴圈適合長規律序列；逐步代理較適合依新觀察分岔，不能把一種介面稱為全面較佳。

## 4. 第一性原理：執行契約需要可觀察、不可繞過

**最小必要狀態（本筆記抽象）**是目前任務、可用技能、技能前置條件、執行中狀態、取消／deadline，以及足以支持 guard 的感測回饋。保留所有影像或長對話不是最低要求；但刪除定位可信度或執行效果，就會把錯誤 status 當世界狀態。

方法有效的條件：guard 能以足夠新鮮的訊號觀察條件；Actor 不能改寫或繞過 guard；底層控制器真正接受停止；技能失敗回饋可供後續決策使用。模型比較慢不必然造成停止慢，前提是兩個時鐘確實隔離。

方法仍可能失效：感知錯誤不一定觸發 guard；固定技能／護欄沒有覆蓋新的危害；本地排程或控制器停止失效；場景先驗過期；長且規律的程序被拆成太多昂貴模型呼叫。作者亦指出新增能力需要技能編寫與平台整合，未解決不完整或歧義證據的可靠傳達。

## 5. 可複用問題與後續驗證

1. 將技能、提示與模型固定，單獨比較啟動前檢查／每 tick guard；量測最壞停止延遲、漏觸發率及資源競爭下的實體停止距離，能否補齊因果證據？
2. 避免人工修正的場景先驗，加入動態物體與過期地圖後，結構化失敗回饋還能維持增益嗎？
3. 把規律子程序封裝成固定技能、只在重要觀察點呼叫 Actor，能否兼得 CaP-X 的規律序列效率與逐步代理的恢復能力？
