    AW-0：程式能改善動作預測，不代表應該直接執行¶

    問題：把程式放進世界動作模型，究竟是更好的規劃表徵，還是更可靠的控制通道？ 讀到的機制：code → video → action 的有向聯合去噪，把技能程式當條件；另一個 hybrid 模式才真正呼叫技能 API。 目前判斷：實驗支持結構化條件的價值，但「可執行」與「值得取代動作 chunk」必須分帳；模擬 hybrid 的資料也不同，不能當純執行切換的消融。

    以下結果都是作者報告，本筆記只分析其比較口徑及證據能支持到哪裡。

    1. 研究缺口：預測未來，還缺什麼？¶

    世界動作模型（WAM）共同預測未來影像和控制訊號，卻不必然表達「先用哪個技能、作用在哪個物件、重複幾次」。外部 Code-as-Policies（CaP）則能組合 API，但物理執行受限於感知及技能實作，也不必然具有學得的未來動態。

    AW-0 想把兩者接起來。真正的新問題不是「機器人會寫 Python」；而是：有物件、參數與技能呼叫的規劃介面，能否在連續控制生成期間提供有用的條件？同一份介面又何時值得直接執行？ 這兩個假說要用不同證據測試。

    2. 任務、輸入輸出與資訊流¶

    以較不混淆的符號重述原文 §2 的生成任務：

    \[ p_\theta(C,Z,A\mid X_t),\qquad X_t=(O_t,L,S_t,M_t). \]

    \(\theta\) 是模型參數；\(O_t\) 是當前多視角影像，\(L\) 是語言指令，\(S_t\) 是機器人狀態，\(M_t\) 是先前程式片段的壓縮記憶；\(C\) 是下一段技能程式 token，\(Z\) 是未來影片的連續 latent，\(A\) 是未來動作序列。下標 \(t\) 表示當前規劃點。這是條件生成分布，不是安全約束、物理模擬器正確性或完成任務的保證。

    三個 transformer expert 各保有自己的投影與 FFN，在每層共享 masked attention。同 expert 內雙向，跨 expert 依 code → video → action 的 blockwise causal 順序傳遞資訊：video 能讀 code，action 能讀 code 與 video，不能把「共同去噪」理解成三者任意雙向驗證。

    • 程式 expert：SDAR-1.7B 初始化，搭配凍結的 Qwen3-VL 視覺塔；部分語言參數凍結，訓練 attention／調變與視覺 merger 等介面。
    • 影片 expert：Cosmos-Predict2.5-2B 初始化的 DiT，使用凍結 Wan2.2 VAE；不是從零學一個完整物理世界。
    • 動作 expert：另設 action DiT。真機採 64 維統一空間；每側含末端姿態、22 維手關節及夾爪寬度，不使用的具身維度填零；RoboTwin 是 14 維，不能混稱所有設定都輸出 64 維。

    附錄 A 的預設動作 horizon 為 32；每視角訓練窗含 9 張影格、步距 4，只有第一張用作當前觀測。未來影片是學習／生成目標，不是推論時偷看真實未來。

    3. 資料怎樣變成可學的程式？¶

    標註管線先從每任務取一集，用 Gemini 3.1 Pro 根據子任務及畫面，針對 declaration-only API 寫程式；Claude Code／Claude Opus 4.8 作 coordinator，將跨任務重複流程提煉成技能。這些模型是作者所用的離線標註工具，不是每個控制步都在線呼叫它們。

    技能庫固定後，重標初始樣本，建立 subtask-to-program cache；其餘片段在接觸與運動證據相符時重用，不符則產生新標註。YAM 與人類各有技能庫，總共 50 項（23／27）。附錄 K 的准入條件包括參數化、至少跨兩任務出現、不是整個任務食譜且不重複。

    重要限制：標註的靜態檢查是語法、函式存在、引數綁定、詞彙等，不是物理執行驗證。YAM 使用感測導出的夾爪事件清單核對接觸順序；人類資料則從畫面推斷，兩者證據強度不同。人類語意 API 不等於已可部署的靈巧手控制器。

    資料量按 B.1 比導論約數更精確：YAM 約 1,919.3 小時、73,101 episodes；人類約 993.9 小時、175,541 episodes。人類頭戴視角複製進三個輸入槽，不是三個獨立視角。下游仍需任務示範再標註、共同微調；這不是零樣本機器人部署。

    4. 訓練與推論：結構是怎樣被消費的？¶

    影片與動作採 flow matching，回歸從資料／噪聲混合狀態復原所需的速度場；程式採 masked-token diffusion，只在遮住的程式位置計 cross-entropy。三個目標共同訓練；原文另對影片噪聲重採樣與 importance weighting，避免只在高噪聲影片下學到不足以引導動作的特徵。

    用原文 §2.2／附錄 A 的目標結構概括：

    \[ \mathcal L=\mathbb E[\lambda_v\bar w_v\ell_v+\bar w_g(\lambda_a\ell_a+\lambda_c\ell_c)]. \]

    \(\ell_v,\ell_a\) 是影片／動作的 flow-matching loss，\(\ell_c\) 是遮罩程式的分類 loss；\(\lambda_v,\lambda_a,\lambda_c\) 是相對權重；\(\bar w_v,\bar w_g\) 是按抽樣密度修正、截斷並以 batch 平均正規化的權重。期望值涵蓋資料與腐化抽樣。這只描述訓練風險，不能把較低 loss 當作技能的物理有效性證明。

    每次重規劃時重建 prompt，加入預設 128 個 mask token 的程式 canvas，以預設 4 次聯合去噪逐步固定高信心程式位置，同時更新影片／動作。歷史程式壓縮進可學 memory slots；訓練有機率以自身預測替代歷史標註，推論則每 episode 重設並累積生成片段。本次未讀到具體 slot 數與該替代機率的可靠定值，不自行補數字。

    預設模式不執行程式：程式是 action expert 的規劃條件，最後執行動作 chunk。因此，預設模式的改善不是「Python 控制器比神經網路好」，而是程式結構可能改善神經動作生成。

    5. Hybrid 的實際切換規則：執行嘗試不等於成功¶

    附錄 I 比摘要更值得讀。每輪同時得到動作 chunk 和程式片段，再經 stage、dependency、syntax／whitelist／非空檢查；避免回到已完成／已嘗試的較低 stage，限制同 stage 失敗次數，且不原地修補程式。

    • 未准入程式：播放該輪動作 chunk。
    • 准入程式：直接執行技能 API；即使執行拋例外，也丟棄同輪舊 chunk，下一輪重新觀測與規劃。不能描述成失敗後立刻接上過時 chunk。
    • Algorithm 2 以「未拋例外」把 stage 加入完成集合。這是程式執行狀態，不是獨立物理後置條件已達成。

    這條界線連到 FastHarness：有效格式／無例外不等於環境真的恢復或完成；也連到 RESCUE：選擇另一通道，要測的是相對於不切換的結果，而不是只數通過幾個 gate。

    6. 實驗究竟支持什麼？¶

    模擬：預設條件有用，但隨機化仍重挫¶

    RoboTwin 2.0：50 任務、每任務 50 個 clean 示範；每種設定每任務評估 50 rollouts。比較 π0.5、DreamZero、EgoScale、WLA。

    • Table 1：AW-0 clean 80.8%、random 20.6%，兩設定平均 50.7%；π0.5 對應 54.9%／27.7%／41.3%。
    • 這支持平均表現與 clean 條件的優勢，不支持所有場景勝出：random 下預設 AW-0 低於 π0.5。
    • Hybrid 是 63.1%／29.2%／46.2%。附錄 J.2 明說其訓練示範採 CaP 管線，而預設採 RoboTwin 原生 motion planner；這是資料＋執行配置的整體比較，不是固定模型下只改 arbiter 的因果識別。
    • Hybrid 收資料時可用 privileged object states／grasps 提高效率；作者說評估感知／控制不使用 privileged simulator information。不能把訓練期資訊取得方式省略，也不能反過來誤稱測試偷看真值。

    真機：71.1 是分項 rubric，不是完整成功率¶

    8 任務、兩種雙臂平台；每任務 100 示範，評估 3 個訓練 seed、每 seed 16 rollouts。Table 2 平均 AW-0 71.1%、DreamZero 46.0%、π0.5 43.6%。附錄 E 明定按子步驟加分，所以這是 average rubric score，不能寫「71.1% 的任務完整成功」。本次沒有逐項核對所有 rubric，也未獨立檢查評分一致性或顯著性。

    真機 Fold／Stack Towels 的 hybrid 採同一 post-trained 模型及評估條件，報 90.6% 對 84.4%，比模擬更接近固定模型的切換比較，但仍只是一個 YAM 任務的分項分數；不能外推靈巧手或全任務 hybrid。

    外部 baseline 並非等同預訓練／算力：C 中 π0.5 真機微調 50 epochs、DreamZero 10，AW-0 A 中是 20，初始化也不同。主榜是系統配置比較，不可把所有差距全歸因 code。更有識別力的是下一組同預訓練資料／budget 的內部消融。

    消融：支持結構，但還不是語意正確性保證¶

    • 注意力順序（Fig. 5）：比較無 code、video → code → action、code → video → action；作者說共用預訓練資料／budget。支持讓規劃參與影片與動作生成，但不等於每一行程式都忠實描述動作。
    • 視覺 grounding（Table 3）：獨立 ViT 對 VAE 特徵平均 rubric 71.1 對 55.6，支持語意視覺條件的價值。
    • 標註內容（Fig. 7）：移除註解、技能呼叫、改語言 subgoal 都有不同退步；完整程式不是每一任務都贏 subgoal。這些變體也改變資訊內容／壓縮方式，不單獨證明 Python 語法本身最優。
    • 共同去噪對 AR（Table 4）：平均 71.1 對 54.5；Replace Lightbulb 是 AR 較佳，不能稱全面勝出。
    • 程式品質（F.1）：預訓練驗證集 parse rate 87.5%，entity F1 0.534、primitive F1 0.365；打亂視覺令 loss 上升支持依賴畫面，但不是所有物件參數都正確。參考標註本身由管線產生，不是絕對語意真值。

    成本與失效¶

    RTX 5090 上作者量得共同去噪 0.23 秒，AR 0.55 秒，無 code 0.19 秒；A 說含視覺編碼、去噪、影片解碼與 action 後處理。這是模型推論計時，未據此證明涵蓋攝影曝光、傳輸、API 執行與機器人致動的整輪延遲，更不適用把標註用大型模型在線加入之後的成本。

    L 明列技能覆蓋／自動標註依賴、參數錯誤與視覺分布外失效；沒有在線從自身互動持續學習。J.2 還指出 validity-only arbiter 不估計切換是否有利。成功 episodes 中 code 占 random steps 的 35.0%，全部 episodes 混合則只有 5.6%；兩個分母不可互換，也不能用成功子集比例宣告整體自主接管率。

    7. 第一性原理：最小必要狀態不只是一段合法程式¶

    1. 規劃條件的必要狀態：物件身份／目前階段／接觸與動作意圖必須能由觀測、狀態及歷史分辨。程式把它們壓縮成可消費的條件，但無法從完全遮擋的畫面恢復沒有觀測到的真相。
    2. 執行接管的必要狀態：還需當前技能前置條件、grounding 可靠度、預期後置條件及可被驗證的進度。語法合法與 namespace 完整只排除程式層錯誤，沒有排除空抓、錯物件或有害接觸。
    3. 有效條件：資料中的技能分解具有跨任務穩定性，視覺能對準參數，策略確實消費規劃，底層 API 能在當前物理／時序條件履約。任一環節失真，都可能讓漂亮程式變成錯誤的強條件。
    4. 物理與資料限制：靈巧手的可執行技能不會因人類語意標註自動存在；共同生成的影片也不是獨立感測器。仍需 BT-Agent 的本地護欄及 Chronos 的時間有效性，不能把模型內一致性當作外部安全證據。

    可重用研究模型：依序驗證「表徵是否增加可用資訊 → 動作是否因而改善 → 替代控制通道是否真正更有利 → 物理後置條件是否被獨立確認」。四關需要不同的消融與量測，不能用主榜一個平均分數代替。

    8. 後續驗證問題¶

    1. 固定預訓練、示範、模型及重規劃時機，只切換 direct／validity gate／advantage-aware gate；能否分開測完整成功、損失、耗時與技能嘗試失敗？
    2. 對程式做物件參數、技能名稱、註解的配對反事實替換，控制長度與算力，動作是否依預期改變？錯程式能否被真實觀測校正，而不是自洽地帶錯？
    3. 將「無例外即完成」改成外部感測後置條件，面對空抓、打滑、遮擋及過時變數時，能否降低誤報完成而不失去速度？
