    ACE-CaP-0：經驗取得成本與凍結程式可靠度要分帳¶

    研究問題不是「LLM 能否再寫一段機器人程式」，而是開發卡住時，下一筆證據應來自示範、模擬，還是真機。 方法把請求示範與按需模擬放進程式修訂迴圈，部署則凍結程式、保留感知與控制回饋。 真機重複執行支持的是所選程式的可靠度；單次開發、示範成本漏帳，仍不足以證明開發流程穩定省人力。

    1. 缺口：執行失敗，不一定告訴開發者下一步怎麼改¶

    既有 Code-as-Policies 把任務邏輯寫成程式，避免每個動作都再問大型模型。但「寫—跑—看—改」仍可能陷在抓法、接近方向與雙臂協調的搜尋中。任務指令只給目標；一次失敗也可能同時相容於感測錯誤、幾何假設不對與動作策略不適合。

    作者因此把改程式與取得能辨識修改方向的經驗放到同一層決策。相對於單純多試幾次，新意是讓 coding agent 選擇何時要人操作機器人的示範，以及模擬應回答哪一個當前問題。它是開發配方，不是提出新的 VLA 訓練架構，也不是證明最優的實驗選擇演算法。（§1–3）

    2. 方法：開發時取得證據，部署時執行固定規則¶

    任務、輸入與輸出¶

    開發輸入是任務指令、工作區觀測、感知與控制介面。工作產物是可執行程式，內容包括動作次序、幾何計算、運動參數與夾爪命令；最終輸出是經壓縮整理後凍結的 task-specific code policy。§4 使用 Claude Opus 5.5 作 coding agent；本文按作者實驗設定記錄，不另推論其普遍模型排名。（§3.1、§3.4、§4.1）

    一輪修訂實際做什麼¶

    1. 讀目前程式、已知證據與未解問題。
    2. 直接修碼，或選擇請求示範、組織模擬、執行真機候選程式；不是每輪都必須做三者。
    3. 示範給出可行動作參考；模擬比較候選實作；真機測試感測與接觸假設是否成立。
    4. 將結果回寫程式，也可更換模擬起始狀態、縮小待測段落、修改模擬器或再請求示範。
    5. 開發結束後凍結程式，獨立評估，不在測試中繼續修碼。（§3.1–3.4）

    示範不是只有影片。 人以 kinesthetic demonstration 直接引導機械臂，記錄影片、臂軌跡及關鍵關節姿態；另可提供文字建議。影片解釋物件互動，機器人軌跡與姿態則限制如何在目標 embodiment 上實作。這與只看人的手、再猜夾爪與雙臂配置不同。（§2.1、§3.2）

    模擬不是先造完整數位分身。 agent 可用現有模擬器，或為當前問題建構／修改環境，選定任務段落、初態與候選程式。避障路徑與接觸行為需要不同的模型忠實度；模擬支持的結論只適用於該次問題與條件，之後仍回真機檢查。論文沒有在方法主文給出一個通用的模擬可信度閾值，也沒有形式化的「何時值得請示範」最適準則。（§3.3、§6）

    資料、訓練目標與控制迴圈¶

    這裡累積的是示範、執行回饋、模擬實驗與程式修訂，不是收集資料後反向傳播訓練一個新控制網路。方法主文未提出新的參數訓練 loss；不要把語言模型產生／修訂程式叫作本文已訓練出通用動作模型。

    部署仍讀取即時觀測，經固定規則計算後呼叫控制介面。凍結的是規則，不是把一條固定軌跡盲目重播；拿掉的是 coding agent／人的逐步決策，不是拿掉所有感知與控制元件。 不過感知工具本身提供多少能力、控制頻率、碰撞防護與急停細節，不能僅由這個概念流程補成已驗證規格。（§3.4、§5.1）

    3. 比較：先分清「流程試驗」與「成品測試」¶

    充電器插入：六個開發條件，不是六組多種子平均¶

    §2 每條件只有一次獨立開發；其選定程式各做 30 次真機評估。共享 reference 是「按需文字＋機器人示範、無模擬」，在三張比較圖中重用，不能把它算三次獨立複現。

    • 示範形式：純文字 60%；文字＋人手影片 73.3%（22/30）；文字＋機器人示範 86.7%（26/30）。後兩者開發時間分別 3.8、3.7 小時；純文字 5.9 小時。這支持本次目標 embodiment 的動作參考有價值，但未隔離影片、軌跡與關鍵姿態各自的貢獻。
    • 提供時機：一開始給文字與機器人示範，53.3%（16/30）、7.2 小時；按需提供，86.7%、3.7 小時。這不是已做等示範內容／數量的因子消融；單次開發也不能排除不同探索路徑的影響。
    • 模擬時機：按需模擬 100%、2.6 小時、1.09M 輸出 tokens；無模擬 reference 為 86.7%、3.7 小時、0.73M。時間下降伴隨 token 增加，不是所有資源都下降。
    • 順序 Real–Sim–Real：先取示範、建模，再在四個平行環境做十輪模擬探索，轉回真機後 0%、3.5 小時、1.86M tokens。它與按需方案還同時差在示範時機、實體回饋時機及模擬配置，不能將差距全部歸因於「使用模擬」或「按需」單一元件。（§2.1–2.2）

    失敗機制比勝負名稱更值得保留¶

    順序方案在抓取插頭就失敗，尚未進入插入。作者指出模擬影像較乾淨、深度不含真機近距離盲區，依據那些觀測改出的抓取程式因而可能無法轉移。正文措辭是與 observation mismatch 一致，不是已完成逐因果消融。（§2.2）

    本筆記判讀：若失敗主要在感測可用性，單純加強接觸物理或延長模擬訓練未必處理真正缺口。應先問「程式依賴的量，在實體部署時能否觀測」，再問模擬成功率。

    八項真機成品：可靠執行，不等於可重複開發¶

    平台是雙 Agilex PIPERX 手臂、三台 Orbbec DaBai DC1 相機（一頂視、兩腕部）。八個凍結 task programs 各評估 30 次，共 221/240 成功；不是公開標準資料集上的跨模型排行榜。（§4、Table 1）

    • 插充電器 30/30；麵包裝箱 25/30；開瓶蓋 27/30；杯子套疊 28/30。
    • 插花 27/30；雞肉擺盤 29/30；包裹轉向 28/30；鞋子裝盒 27/30。
    • 指標是達成各任務目標的 success rate，及平均 physical execution time。各任務時間介於 0.97–2.27 分鐘；這不是包含前置開發、示範及重置的端到端交付時間。
    • 八任務展示沒有同表 VLA／WAM 或各 recipe 變體的全任務對照；§2 的開發條件比較只在插充電器做。不能據此聲稱全面超越那些路線。
    • 麵包裝箱分數最低，但已讀正文沒有將其五次失敗逐項分類；不自行補寫成「軟物體抓取造成」。新物件、布局、跨任務技能重用與獨立開發重複性，也不是這組重複執行已證明的結果。（§4、§6）

    4. 第一性原理：有限預算究竟限制了什麼？¶

    最小必要狀態有兩層。開發層至少要知道目前程式、哪個假設未決、各來源已提供何種證據；執行層則要保留足以計算抓取、對位與協調的即時觀測。若示範只提供動作順序卻沒有可實現姿態，或模擬保留幾何但丟掉感測盲區，壓縮掉的可能正是決策所需資訊。

    每任務最多十次 human-assisted scene resets，不含收示範用的重置，且自主執行與示範本身不計入該預算。因此「十次重置」不能換句話寫成十次試作或最多十次人工介入；它只界定其中一項稀缺資源。（§2 shared setting、§3.1、§4.1）

    為避免混帳，可另用下式整理未來需量測的完整開發成本；這是本筆記提出的會計框架，不是原文的 loss：

    \[ C_{\mathrm{dev}}=C_{\mathrm{model}}+C_{\mathrm{sim}}+C_{\mathrm{robot}}+C_{\mathrm{demo}}+C_{\mathrm{reset}}. \]

    其中 \(C_{\mathrm{dev}}\) 是開發總成本；後五項分別是模型、模擬、真機運作、示範蒐集與場景重置成本。相加之前必須統一成金額或明確加權尺度，且避免把已含在 elapsed time 的部分重複計費；若不能統一，就分列工時、token、機時而不強加總。原文報開發牆鐘時間與輸出 tokens，但 §6 也明說後續要把示範努力納入成本，不能用 token 節省替代人力節省。

    有效條件：任務能壓縮為穩定程式規則、示範能提供目標 embodiment 的可行參考、模擬針對的問題具有足夠忠實度，且真機回饋能及時暴露錯誤假設。

    可能失效：場景超出固定規則支援範圍、關鍵狀態不可觀測、接觸／感測誤差改變候選排序、agent 反覆索取高成本示範。反過來，即使某個凍結程式 30/30 成功，也不代表開發程序下次仍能在相同預算內找出它；作者 §6 已明確區分 repeated execution 與 independent development runs。

    5. 可複用研究問題與後續驗證¶

    1. 真正等成本比較：多任務、多次獨立開發，固定示範內容與上限，將示範／人工／模型／機時分列，是否仍得到按需方案的優勢？不要以同一成品的更多 rollouts 取代重複開發。
    2. 模擬的決策有效性：對相同候選程式記錄模擬排序與真機排序；分別介入感測盲區、幾何與接觸誤差，哪一類失配會使模擬建議變差？要量化「可支持哪種決策」，而非只評影像逼真。
    3. 凍結後如何失效與交還控制：換物件／布局、感測缺失與執行失敗時，程式是否識別不適用並停止／交還？另測安全事件與完整任務成功；本篇成品成功率不是持續安全保證。
