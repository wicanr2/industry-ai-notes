# 雙臂操作：把可達條件寫進計畫，仍要分開局部恢復與安全驗證

> **問題**：語言模型知道先移障礙再取物，為何仍選到夾爪進不去的方向？
> **方法**：把物件各側的空間、逆運動學可達性與阻擋原因交給規劃器，再用階段條件與嘗試歷史決定重試、改參數或重規劃。
> **判讀**：真機對照支持顯式執行資訊與局部恢復的價值，但驗證器仍是 VLM；成功條件、查詢節省、物理安全與整體牆鐘效率必須分開。

## 1. 缺口不是少了一段「先移障礙」的語言推理

原文區分物件的語意／空間關係與真正可執行的接觸。例如「藍盒在白盒旁邊」沒有告訴模型兩者間距是否容得下夾爪；「物件左側沒有遮擋」也不代表左臂在當前姿態有可行關節解。雙臂又多了手臂分配與同時動作是否互相衝突的問題。

**本筆記判讀**：核心不是讓 VLM 憑畫面想得更仔細，而是先把控制所需的條件算出來，再讓規劃、排程與恢復共用這些條件。這縮短「選了什麼」與「為何做不到」之間的歸因距離，沒有消除感知與控制誤差。

## 2. 任務、輸入輸出與必要假設

任務是在桌面雜亂場景中依自然語言取物、移動障礙與協調雙臂。輸入是任務指令、機器人視角 RGB、物件尺寸／姿態與機器人可達性；輸出經過四個層次：場景表示 → 有序操作 → 可並行階段及條件 → 低階執行與階段驗證。

物件用有方向包圍盒表示，六個側面名稱相對於機器人，而非物件固有正面。框架假定可由一對平行相對面夾取；指定必須抓杯柄等 instance-specific affordance 不在範圍內。姿態由 **FoundationPose 的 model-based 模式配合物件 CAD 模型**取得，不能把它寫成無先驗開放世界取物。

真機為 CENTAURO，兩支六自由度手臂配 Dagana 夾爪；所有實驗底座固定。動作由 QP-based inverse kinematics 產生關節參考，並非 VLM 直接輸出馬達命令，也不是本文新訓練的端到端 VLA。

## 3. 方法真正改了什麼？

### 3.1 場景狀態：把可接近、可達與原因分帳

依 §III B，時刻 $t$ 的場景圖是

$$G_t=(V_t,R_t),\qquad V_t=O_t\cup E_t.$$

這裡 $O_t$ 是物件節點，$E_t$ 是末端執行器節點，$R_t$ 是節點間關係；$t$ 代表更新時刻。VLM 先辨認物件、顏色／易碎性與 on-top-of、right-of、in-front-of、grasped-by 等關係；夾爪另記空手或持物狀態。

幾何資料再補兩種不同條件：

- **Accessibility**：依相對物件面距離與由夾爪幾何決定的間隙門檻，判斷該側是否有空間接近；若被擋，保存阻擋物或支撐面。
- **Reachability**：對候選側的接近姿態檢查是否有可行逆運動學解。

白話說，前者問「工具塞得進去嗎」，後者問「手臂到得了嗎」。這不是連續路徑無碰撞或接觸力安全證明；主文未完整給間隙數值、感知誤差傳播與所有路徑驗證規格。

### 3.2 規劃與排程：從動作名稱展開物理選擇

§III C 的單一步驟寫成

$$a_k=(\mathrm{action}_k,\mathrm{target}_k,\mathrm{mode}_k,\mathrm{contact}_k,\mathrm{side}_k).$$

$k$ 是操作序號；action 為 grasp／place／push／release，target 是目標物或放置目的地，mode 是左臂／右臂／雙臂，contact 記是否使用 claw，side 指接觸面或相對面組。這些是動作規格，不是可由模型自由發明的新技能。

規劃器先找可行抓取方向；沒有才用阻擋原因選要搬走的物件。障礙物放置以參考物定義相對位置，需滿足同一間隙門檻，避免只從眼前移走卻堵住下一步；易碎等語意約束會影響推動／抓取選擇。

排程模組把序列中相容操作併成階段，檢查物件交互作用、空間與手臂配置，並產生該階段的局部目標、前置與後置原子條件。**主文沒有提供可機械重建全部排程判準的完整規則或形式化正確性證明**；不可把文字上的「避免衝突」升格為經認證的雙臂安全排程器。

### 3.3 閉迴圈：先補證據，再決定修多大

§III E 的每個條件 $c$ 由 VLM 輸出

$$v(Z,c)\in\{\text{satisfied},\text{uncertain},\text{violated}\}.$$

$Z$ 是當次可用視覺證據；前置檢查用當前影像，後置檢查用前後影像加已執行操作。階段聚合規則是：任何條件 violated 則失敗；否則有 uncertain 則不確定；全數 satisfied 才通過。這是**離散判定，不是經校準機率或安全界限**。

不確定時先重建場景圖、加證據後再檢查；確認失敗或歧義持續才進恢復。前置不滿足時尚未執行，直接重規劃；後置失敗時將未滿足條件、理由、前後場景與該階段歷史一起交給恢復：

1. **Repeat**：有部分進度但未完成，重新感知後照原規格再做。
2. **Modify**：可歸因到操作參數，Action Revision VLM 參考歷次影像／失敗條件，修改手臂配置、claw 使用或接觸面，再執行。
3. **Replan**：原階段已不適用、資訊仍不足或無局部策略可支持時，重做感知、剩餘規劃與排程；把失敗摘要和已試策略帶回規劃器。
4. **Abort**：用盡允許嘗試仍無可行策略時停止。

歷史保存已試策略以免無效循環。主文未完整公布各層嘗試次數與所有 decision prompt；可理解流程，但不宜宣稱僅憑主文可逐位元重現。任務完成定義為所有階段後置條件被驗證 satisfied，而不是外部安全監督器認證。

### 3.4 資料與訓練：這是一套推論系統，不是新 loss

作者稱 zero-shot，具體是**沒有任務專屬訓練、微調或示範**；預訓練 VLM 與 FoundationPose 並非沒有訓練資料。預設 VLM 為 Gemini Robotics-ER 1.6，另做 backbone 替換。本文沒有新的訓練資料集、損失函數或 reward optimization；不應為套格式而補出不存在的訓練目標。

## 4. 實驗究竟支持哪一段？

### 設定、指標與公平比較

§IV 在九個真機桌面情境中，**每情境從相同初始配置執行 20 次**；這測固定配置重複可靠度，不是 20 個獨立新布局。沒有大型公開跨場景測試集。三種配置共用 VLM、指令、操作 primitives 與低階模組：

- 非 execution-aware 場景＋binary validation。
- execution-aware 場景＋binary validation。
- execution-aware 場景＋hierarchical validation（完整方法）。

前兩者用二元驗證，失敗一律重規劃。這讓新增執行資訊與新增恢復策略能逐層比較；但**沒有「非 execution-aware＋hierarchical」第四格**，也未單獨移除 accessibility／reachability，不能完整分解交互作用或兩種資訊的各自因果效果。

Table III 的 SR 是執行成功百分比；Queries 是**僅成功執行**的平均 VLM 呼叫數。模組 SR 則以模組全部呼叫為分母，Latency 是單次呼叫平均秒數，驗證延遲為前／後檢查平均。不可把這幾種分母混用。

### 主表的機制與反例

以下依序列「非執行感知／執行感知＋二元／完整」的 SR，均為作者 Table III 報告：

- **Boxes Aside：0%／75%／85%**；明確間隙資訊讓規劃器不再直接嘗試被側向堵住的抓取。
- **Fragile Box：0%／70%／70%**；執行資訊有幫助，但 hierarchical 沒有再提高成功率。
- **Long Horizon：0%／35%／50%**；改善仍不等於長程任務可靠，完整方法依然只有半數成功。
- **Stacked Boxes：三者均 100%**；當「在上方」的符號關係已足夠時，新增幾何資訊不一定再有收益。
- **Scene Update：三者均 85%**；場景改變常必須重規劃，局部策略並非通用替代。
- **Bottle Failure：三者均 90%**，但完整方法成功 run 的平均 queries 從二元方案 10 降至 8.1；此處主要改善是查詢數，而非成功率。

**本筆記判讀**：最強證據是側向障礙與接觸選擇錯誤下的局部對照，不是已證明能處理任意家庭場景。表格未報信賴區間或顯著性檢定；少量固定配置重複不可當成廣泛分布保證。

### 「恢復便宜」的兩個口徑陷阱

Fig. 5 的每次恢復決策，repeat／modify／replan 分別重叫 1／2／3 個模組；平均成本以成功執行中的恢復決策計，**不含重做階段的 validation calls**。Bottle Failure 報 1.1 對二元重規劃 3；Push Failure 報 2.1 對 3。它證明某些修正少重叫模組，不能直接推出所有嘗試的平均成本、token 費用或尾延遲較低。

Fig. 6 的並行排程展示：Bottles on Box 動作時間由 60 秒到 36 秒、階段 5 到 3；Long Horizon 108 秒到 96 秒、階段 9 到 8。作者特別說**不是 20 runs 的平均**，且只計機器人運動、不計模型查詢。不可把它寫成完整系統牆鐘吞吐改善 40%。

Table IV 在三個代表情境比較 backbone：Gemini Robotics-ER 1.6 為 SR 73.3%、latency 41.9 秒；o3 為 80.0%、91.4 秒；GPT-5.2 為 5.0%、34.6 秒。這裡 latency 是四類模組的平均延遲之和，**不是每任務總完成時間**。結果表明此介面對 backbone 很敏感，不是通用模型能力排名；未核模型服務參數及完整 prompts，不能外推其他部署配置。

## 5. 第一性原理：最小必要狀態，與它仍漏掉什麼

為了在失敗後知道要修哪裡，最少需要：物件身分／姿態、哪個面被誰擋、各手臂可達性、夾爪持物狀態、當前階段的預期效果，以及已試過哪些參數。只保存「失敗」標籤會丟掉局部修正依據；只保存完整影像但不對齊動作選擇，也可能難以歸因。

有效條件是：盒形／平行夾取近似合理、CAD 姿態可用、場景變化慢於高階推論、失敗能由影像與階段條件看出，而且局部修正不破壞後續計畫。技術／資料／物理邊界則包括：

- **感知共因錯誤**：VLM 的感知與驗證可能共同誤認；「後置條件通過」未必是真實效果。作者提到視角、透視與頭部相機不佳位置造成錯誤，沒有獨立外部真值驗證所有判定。
- **接觸與路徑**：幾何間隙／IK 解沒有覆蓋摩擦、物件滑動、受力及完整 swept-volume；不能拿局部條件當安全屏障。
- **移動性被固定**：固定底座使某些方向直接被淘汰；未測移動底座如何改可達性、視野與安全。
- **恢復歷史不是保證終止品質**：有嘗試上限可停止迴圈，但不代表知道何時停止才最安全；主文也未量化 false-satisfied 與誤中止成本。
- **成功樣本的成本偏差**：效率應另報所有嘗試、失敗與 abort 的資源，不以成功 run 篩過的便宜結果代替部署平均。

## 6. 可複用研究問題與下一證據

1. **資訊與恢復各救了什麼？** 做完整 2×2 因子試驗，再分別移除 accessibility、reachability 和失敗歷史；固定布局分布、backbone、預算，分報完整成功與失敗類型，而非只比較完整方法和弱基線。
2. **驗證器真的知道何時不知道嗎？** 用獨立姿態／接觸真值標記前後條件，測 satisfied／uncertain／violated 的誤判；注入遮擋、CAD 尺寸誤差與接觸滑動，觀察錯誤通過與停止距離，不只看最終任務 SR。
3. **少查詢是否真的更快更划算？** 對所有 run 計入 perception、規劃、validation、重試運動、失敗與 abort 的總牆鐘／token／人工救援；比較同期限下成功率及尾延遲，並保留物理安全獨立門檻。

與 [AMP1 的在線程式／定時軌跡](../2026-11-10/01-amp1-直接控制要分開策略修正時間與恢復權限.md)對讀：本文刻意限制在固定 primitives、修少量操作參數；AMP1 允許更直接的策略修正。這是**修正權限粒度**的比較，未有兩者相同任務／預算的實測。也接回 [Nav2 的語意、提交與物理守界](../2026-10-27/01-nav2-政策合法不等於指令正確或物理安全.md)：把條件寫進資料結構，不代表下游已完整遵守或安全；三篇未驗證彼此整合。

## 可放進資料庫的一句話

把執行條件與阻擋原因顯式化，能讓規劃和恢復共享可檢查的狀態；真正部署仍需另證條件感知可信、局部修正不破壞後續、且節省查詢能轉成全任務收益，而不是把 VLM 判定通過當成物理安全。
