# TWCA 換證：分開序號合規、憑證鏈與服務驗收

> 問題不只在「新憑證是否產製」，而在舊中繼憑證廢止前，依賴它的服務能否完成切換。
>
> 公開事件追蹤另揭露一個重要區分：CA 憑證的 24-bit 問題，與訂戶憑證的 63-bit 問題，不是同一種序號結構。
>
> 因此要分別驗證合規修正、完整鏈部署與終端連線；沒有已知入侵，不等於沒有服務連續性風險。

## 核心命題：修正可以集中生產，完成卻要分散驗收

發證端能批次重新簽發，網站與設備端卻各有部署權、維護窗口與相依設定。主管機關採購一項共用服務，不代表能在同一瞬間替所有終端完成更新。**供應商交付檔案，是服務復原鏈的輸入，不是完成證明。**這是本筆記的機制推論；不表示本輪已發現哪個具名網站失敗。

同時，技術缺失要先定義對象。若把「所有憑證」當成一種物件，會把兩件合規問題混為一談，也可能把序號不足錯讀成私鑰強度不足。

## 證據鏈：哪些已披露，哪些仍待驗證

### 1. 24、63、64、128，說的是不同東西

**主管機關說法**：數發部描述部分憑證序號長度為 128 bits，但有效隨機內容只有 24 bits，並列政府端受影響數量。公告沒有把不同憑證層級完整拆開。

**外部研究者主張**：2087236 初報討論的是 **CA 憑證**，其序號含固定結構、日期／計數欄與最多 24 bits 表面隨機內容；研究者明言該報告沒有指稱訂戶憑證存在同一問題。研究者列出樣本及簽章歸屬方法，但本筆記未重做驗證。

**供應商新增確認**：2087236 comment 5 明確說的是 **subscriber certificates（訂戶／終端憑證）**，確認其中受影響序號含 63 bits 而非所要求最低 64 bits 的 CSPRNG 輸出；總母體仍在確認。2087918 則記錄另一種序號排列與樣本。

**本筆記判斷**：兩項事件可放在同一治理調查，不能把「24 bits」直接套到 9,772 張政府網站憑證各自的序號。政府端數字是部署影響統計，不是研究者 CA 憑證樣本數。來源表述層級不同時，保留差異，不用官方身分或報導篇數替代物件定義。

CSPRNG 是供密碼系統使用的偽隨機數產生器。此處規範要求的是序號含多少生成器輸出，**不是 TLS 加密金鑰長度**；128-bit 欄位總長也不能保證有同樣多的隨機內容。本文不由序號數字推導破解機率、私鑰可猜性或已發生偽造。

### 2. 重新產製和完成更新是兩個官方數字

**數發部披露**：事件涉及 962 個政府機關、9,772 張網站憑證；TWCA 已於 11-01 完成政府端新憑證產製，經郵件主動補發。截至 11-02 晚間，有 926 張完成更新。

以同一公告的張數口徑計算：926 ÷ 9,772 約 **9.48%**，差額為 **8,846 張**。算術以 Python 執行；這只能叫「該時點公告的更新比例／差額」，不能叫 11-04 尚未更新數，更不能叫剩餘網站或機關數。一個機關可有多張憑證，憑證張數也未必與獨立網站一對一。

**缺口**：公告未定義「完成更新」是否同時包含所有副本、完整憑證鏈與終端驗收；也未給流量、服務重要性或各機關分布。因此不能由 9.48% 推算國民受影響比例，或宣稱另外九成網站即將中斷。

### 3. 期限要看舊中繼憑證，不只看新檔案收到沒

**TWCA 10-31 公告**：原中繼憑證須於 **2026-11-06 00:00 前廢止**，要求在廢止前更換，且安裝須包含完整憑證鏈；重新簽署沿用原金鑰。11-02 說明亦要求伺服器憑證及必要中繼憑證更新後做連線測試。

**本筆記推論**：僅收到郵件、匯入新站台憑證或後台顯示有效期變更，都不足以獨立證明整條服務路徑完成。若還有舊鏈相依或未更新的節點，端點仍可能失敗；這是待驗證的失效路徑，不是本輪觀察結果。公告的零時不應被鬆寫成「11 月 6 日整天都能處理」；其文字未另註時區，實務維護應向供應商確認精確撤銷時點與適用範圍。

### 4. 未見入侵與應否換證，不是互相排斥的結論

**主管機關主張**：目前未造成具體資安危害，仍須盡速更新，將委託第三方深入檢測，並調查違約、依約罰款求償。這是處置承諾，不是檢測完成或已確定賠償金額。

**供應商主張**：本次並非網站遭入侵或私鑰外洩引起。**研究者的限定**：沒有金鑰失陷、濫用或利用的證據，也不主張短序號本身就能偽造 SHA-256 簽章。

**本筆記推論**：攻擊事件、規範符合性、服務可用性是三本帳。缺乏入侵證據不會取消合規修正；必須修正也不能反推已被攻擊。這裡的新增成本主要先體現在換證、驗收、聯繫與調查，實際停機／損失尚無本輪資料。

## 文章段落安排與敘事效果

中央社先給「主管機關已要求修正與調查」，再說序號缺失、受影響規模、產製與更新進度，最後交代第三方檢測及責任。這個次序能先讓讀者知道處置窗口，但也可能讓「完成產製」成為最醒目的完成訊號；必須讀到後段的 926 張，才看到交付與落地的差距。報導主要轉述單一機關，沒有獨立端點抽樣。

數發部原稿的數字與節奏接近，因此媒體和官方不算相互獨立驗證。TWCA 11-02 說明先用「接軌／升級」建立框架，再談通知、安裝與測試；這種寫法可能讓讀者較聚焦服務安排，卻弱化既有規範未符合的歷史。Ballot 164 提醒我們區分「規範本次提高」與「既有要求本次被發現未符合」，但不足以證明誰曾明知而不改。

Bugzilla 則先定義樣本、結構、適用範圍及不主張之處，再留下根因與行動項目待公司補完。其價值在可被重驗的窄命題，不是留言越多就越可信。原初報內文時間線與 API 建立時間亦有日期差異，本篇不使用它推定第一個通報時刻；近期新確認的時間以 API comment 5 為準。不臆測作者或機關心理。

## 第一性原理：信任服務為何有集中缺失、分散成本

- **最基本問題**：連線端能否沿一條可接受的憑證鏈，確認所連服務的身分？發一張新檔不是全部工作。
- **技術約束**：序號欄位長度、CSPRNG 輸出與簽章／私鑰是不同性質；終端與中繼憑證也有不同責任。把不同物件混成單一「憑證安全」分數會丟失關鍵限制。
- **制度約束**：公開信任體系的合規要求會把單一供應商問題傳到客戶部署；政府採購、國際規範與各服務驗收不是同一個權限邊界。
- **時間約束**：批次簽發可集中處理，人工安裝、變更核准與連線測試各有時鐘；硬期限把原本可分散的維護工作集中。
- **誘因與成本**：供應商希望迅速完成補發，機關要兼顧不斷線與變更安全，主管機關要取得進度與責任證據。郵件數容易計量，端到端驗收較昂貴；因此用前者代理後者會產生管理盲點。這是一般誘因分析，不是指控有人刻意錯報。

## 產業機制、替代解釋與反事實

**因果路徑提案**：共同發證依賴 → 共用鏈必須調整 → 客戶在同一窗口更換 → 維運與供應商支援量集中 → 若驗收能力不足，可能增加連線失敗與緊急變更成本。共用服務能降低平時重複成本，也集中事件處理需求；不能直接把集中採購判成錯誤。

9.48% 的早期更新數可能反映剛寄送不久、盤點回報延遲、預排維護窗口，而不必然是機關缺乏能力。若 11-05 前回報快速上升且外部測試通過，便削弱「部署能力是主要瓶頸」的判斷。反過來，若簽發已全數完成，外部鏈驗證仍失敗，才更支持最後一哩問題。

另一替代解釋是統計定義過窄／落後：實際端點已換，管理台尚未回報。要用同時間的部署紀錄與終端測試區分，不能僅比兩則不同時點新聞。若舊中繼仍有其他可接受路徑，也不能由公告期限推定每個客戶端同步拒絕；本輪未核對各平台撤銷行為與替代路徑。

本事件可作 AI／Agent 維運的類比：自動執行依賴身分與服務連續性，但沒有證據顯示特定 AI 系統因此受影響。不要用「AI 基礎設施」四字放大一宗尚未量出損失的憑證事件。

## 追蹤指標與期限

1. **11-05 至公告廢止時點前**：追數發部新披露的更新張數、統計時點及驗收定義；若無新數據，維持未知，不拿 11-02 的差額當倒數儀表板。必要證據是同分母的進度與具代表性的外部連線／鏈檢查。
2. **11-06 後一個工作週**：追實際撤銷範圍、可用性事件、失敗集中於哪些終端與補救成本。不以未見媒體報導當成零事故，也不擅自掃描所有政府端點。
3. **公司承諾完整報告期限**：2087236 comment 3 寫 2026-11-12 19:00 UTC，即 **台北 11-13 03:00**。屆時看 CA／訂戶兩案的母體、序號生成路徑、根因、稽核漏檢與改善驗證；這是公司承諾的回覆時點，不是根因已知或報告必定完成的保證。

## 可重用思考模型：合規、交付、部署、驗收四本帳

碰到批次安全更新或信任基礎設施事件，逐項問：

1. **合規帳**：哪一種物件、哪一條要求、缺失和攻擊證據是否分開？
2. **交付帳**：新版本產製、寄送或下載，證明供應商做到哪一步？
3. **部署帳**：誰有權替換所有依賴，還有哪些節點／維護窗口未涵蓋？
4. **驗收帳**：同一時點、同一分母下，使用端是否真的成功？誰提供失敗證據、誰承擔成本？

可對讀[PHP 修復交付責任鏈](../2026-10-23/02-PHP漏洞要分開發現速度與修復交付.md)：該文區分補丁發布與正在服務的程序真正載入更新。本篇新增的是 CA／訂戶物件差異與中繼憑證切換窗口，不把它當作舊漏洞已惡化的證據。

**仍未知**：全部受影響訂戶母體、11-04 即時部署率、各平台實際撤銷處理、具名端點驗收、已實現停機成本、完整根因及第三方檢測結果。這些缺口不以新聞措辭或自行推算補齊。
